请创建一个名为 **git-commit-cn** 的技能，满足以下严格要求。所有面向用户的描述信息一律使用**中文**，Conventional Commits 的 type 前缀一律使用**英文**。

---

## 一、技能目标

在执行所有与 Git 相关且涉及"描述信息编写"的操作时，统一输出规范：

* 描述内容必须为中文
* 标题前缀（type）必须为英文（遵循 Conventional Commits 风格）

---

## 二、适用范围

该技能必须自动应用于以下场景（包括但不限于）：

* git commit message
* GitHub / GitLab issue 标题与描述
* Pull Request（PR / MR）标题与描述
* changelog 生成
* 代码变更说明（AI 自动生成）

---

## 三、格式规范

### 3.1 标题格式

标题格式必须为：

```
<type>(<scope>): <中文简要描述>
```

说明：

* type：必须为英文，且只能从以下集合中选择：
  `feat, fix, docs, style, refactor, test, chore, perf, build, ci, revert`
* scope：可选（英文），用于标识模块，如 `auth`、`api`、`ui`
* 冒号后内容：必须为中文

示例：

```
feat(auth): 新增用户登录功能
fix(api): 修复获取用户信息接口的异常问题
```

### 3.2 详细描述（body）要求

* 必须使用中文
* 语气专业、简洁
* 如果内容较复杂，使用结构化表达（如分点说明）
* 不允许出现整段英文（除非是代码、命令或专有名词）

### 3.3 禁止行为

* 不允许使用中文作为 type（如"新增"、"修复" ❌）
* 不允许标题全英文
* 不允许中英文混杂（除非必要术语）

---

## 四、自动修正机制

当用户输入不符合规范时，必须自动转换，而不是直接使用：

* 如果用户提供英文描述 → 自动翻译为中文
* 如果缺少 type → 根据语义自动推断（如"修复bug" → `fix`）
* 如果 type 是中文 → 转换为对应英文（如"修复" → `fix`）
* 如果格式不符合 → 自动重写为标准格式

---

## 五、智能推断规则

* "新增 / 添加 / 实现" → `feat`
* "修复 / bug / 错误" → `fix`
* "优化 / 提升性能" → `perf`
* "重构" → `refactor`
* "文档" → `docs`
* "测试" → `test`
* 其他不明确情况 → `chore`

---

## 六、输出要求

技能在生成任何 Git 相关文本时，必须：

1. 严格符合上述格式
2. 优先保证语义清晰，而不是逐字翻译
3. 保持简洁，避免冗长废话

---

## 七、示例转换

输入：

```
fix login bug
```

输出：

```
fix(auth): 修复登录功能中的异常问题
```

输入：

```
新增支付功能
```

输出：

```
feat(payment): 新增支付功能
```

输入：

```
update readme
```

输出：

```
docs: 更新项目说明文档内容
```

---

## 八、扩展能力

该技能应具备以下扩展能力：

* 可用于自动生成 PR 描述（包含变更摘要）
* 可用于生成 issue（问题描述用中文）
* 可统一团队提交风格

---

## 九、请生成的交付物

请基于以上规范生成完整的 skill 定义，包括：

1. `SKILL.md` 主指令文件（含 frontmatter 的 `name` 与 `description`，作为 skill 被 Agent 自动发现与调用的入口）
2. `scripts/validate-commit.sh` 校验脚本（判定一条 commit message 是否满足本规范，供 hook 或 CI 调用）
3. `scripts/format-commit.sh` 格式化脚本（将不规范输入改写为标准格式，体现§四自动修正机制与§五智能推断规则）
4. 关键交互场景示例（至少覆盖：英文输入翻译、中文 type 转换、缺失 type 自动推断、body 结构化分点四种转换路径）
